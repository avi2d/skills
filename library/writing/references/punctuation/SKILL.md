# Punctuation

Each heading is one principle about a mark or a piece of inline markup.

## End the sentence or use a comma

Separate thoughts with a period or a comma, in English and in Russian alike.
An em dash, an en dash, a parenthesis, a hyphen used as a dash and a semicolon each read as a tell, and swapping one for another only trades tells.
An aside that needs brackets is its own sentence, or it goes.

## Use a colon only before a list or an example

A colon that joins two clauses, as in "If you're coming from automation: describe conditions instead", becomes two sentences or one plain one.

## Spell out plurals and alternatives

Write "one or more files", never "file(s)".
Write "a, b, or both", never "a/b" or "and/or".

## Put code in code font

A symbol, a path, a flag or a command goes in code font.
Code spans and code blocks are code, not prose, and keep every mark the code needs.

## Bold a UI element or a lead-in, and nothing else

Bold the name of a UI element the reader acts on, such as **Submit**.
A bold lead-in that ends in a period, names its item and is followed by new detail is fine: "**Schema in TypeScript.** Tables live in one file."
A bold label that restates its line, as in "**Performance:** Performance improved", becomes plain prose, and a proper noun or an acronym stays unbolded.

## Use straight quotes and no decorative emoji

Replace curly quotes with straight ones, and remove emoji from headings and bullets.

## Use the serial comma

Write "red, white, and blue".

## Shape a list for its content

Number a sequence and bullet everything else.
Introduce a list with a complete sentence, and keep its items parallel.
Say up front when a list is partial, rather than ending it with "etc.".

## Make link text name where the link goes

Use the page title or a short description as the link text, never "click here", so the link makes sense out of context.
Prefer a sentence of context on the page over a link off it.
